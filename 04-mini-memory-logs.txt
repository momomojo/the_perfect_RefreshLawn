Stripe & Supabase Integration Audit Report
Date: 2025‑06‑17
Scope: Review of your Expo app’s Stripe integration (Edge Functions, Webhooks, DB schema, migrations, and frontend) versus the live Supabase database.
1. Live Database vs. Local Migrations
1.1 Live Supabase Schema (inspected via MCP)
Your production DB (project lawnrefresh-git-auth) does contain these Stripe‑related tables in public:
customers (PK id, user_id → auth.users(id), UNIQUE stripe_customer_id)
subscriptions (PK id, user_id → auth.users, UNIQUE stripe_subscription_id)
payments (PK id, user_id → auth.users, UNIQUE stripe_payment_id)
invoices (PK id, UNIQUE stripe_invoice_id)
Each has proper foreign keys back to auth.users, customers, or bookings, and appropriate UNIQUE constraints on Stripe IDs.
1.2 Local Migration Files
Your migration folder includes:
Migrations to add Stripe fields (stripe_customer_id on profiles; stripe_product_id/stripe_price_id on services)
Indexes, constraints, triggers, and RLS policies
No explicit migrations that CREATE the customers, subscriptions, payments, or invoices tables.
Gap: The local migration set does not define these four core tables, yet they exist in production. You need to reconcile—either add missing migrations or remove the discrepancy.
2. Code Integration Overview
2.1 Edge Functions & Shared Helpers
Monolith: stripe-api Edge Function (1 000 LOC) handling create-payment-intent, create-customer, subscribe, list/attach/detach payment methods, admin endpoints, etc.
Microservices: Separate Edge Functions under stripe-customer-api, stripe-payment-api, stripe-subscription-api, stripe-admin-api.
Shared utils: _shared/stripe-utils.ts provides a single getStripeCustomerId(userId) with fallback to profiles.
2.2 Webhooks
stripe-webhook function verifies signatures and handles events:
payment_intent.succeeded → payments.insert
customer.subscription.* → subscriptions.insert|update|…
invoice.* → invoices.insert
2.3 Frontend
Web: StripePaymentWeb.tsx using supabase.functions.invoke("stripe-api") → create-payment-intent → stripe.confirmCardPayment.
App: booking.tsx calls stripe-payment-api → create-booking-and-charge (handles booking + payment in one call).
3. Key Issues
3.1 Missing Migrations
customers, subscriptions, payments, invoices tables are not created by any local SQL file—yet they exist live.
Action: Add idempotent Supabase migrations for all Stripe tables (columns, FKs, ENUMs, UNIQUE constraints).
3.2 Inconsistent Customer ID Storage
You store Stripe IDs on both profiles.stripe_customer_id and separate customers table.
_shared/stripe-utils.ts tries profiles as fallback but profiles column is rarely updated.
Action: Pick one: either migrate off profiles.stripe_customer_id into customers entirely (remove the column and fallback code) or unify by syncing both consistently.
3.3 Duplicate Function Code
You maintain two code paths—monolithic stripe-api vs. microservices—often duplicating work (e.g. getStripeCustomerId, attach/detach PM).
Risk: Drift, harder maintenance.
Action: Consolidate on one pattern. Either retire the monolith in favor of specialized functions (already used by your booking screen), or vice versa.
3.4 API Version Mismatch
stripe-api uses apiVersion: "2023‑10‑16" but stripe-webhook uses "2024‑06‑20".
Risk: Webhook payload shapes may differ from client calls.
Action: Standardize on one API version across all functions.
3.5 Webhook Idempotency & Integrity
Handlers do raw INSERT on every event—retrying a Stripe event will duplicate records.
Action:
Add UNIQUE constraints on Stripe IDs (stripe_payment_id, etc.).
Switch to .upsert() or ON CONFLICT DO NOTHING/UPDATE in your webhook code.
3.6 Sensitive Logging
You log partial webhook secret in the Edge Function console.
Action: Remove or fully redact credentials from logs.
3.7 Frontend Header Override
In StripePaymentWeb.tsx, you pass an empty headers object to invoke—likely dropping default Authorization header.
Action: Omit headers override or explicitly re‑pass the JWT so your Edge Function sees the user’s token.
3.8 Billing Details & Fraud/SCA
Your card confirmation omits billing_details (name, address).
Action: Supply billing_details in confirmCardPayment to help fraud checks and SCA compliance.
4. Status Overlap & Confusion
4.1 Booking Status Enum
Your booking.status column uses a custom enum (booking_status) defined (in DB) as:
Apply to 04-mini-memo...
The code’s migrations only ever added 'pending','scheduled','in_progress','completed','cancelled','paid'.
Live DB has a more nuanced workflow; Local migrations are out of sync.
Action: Align migrations and type definition with live enum values.
4.2 Payment Status
You also store a free‑text payments.status and a bookings.payment_status column.
Risk: Users and code may confuse these with booking.status.
Action:
Keep booking.status strictly for the booking workflow.
Use payments.status (or a dedicated payment_status ENUM) for payment‑specific states.
Avoid overloading a single status field.
5. Recommendations
5.1 Consolidate / Migrate Stripe Tables
Add missing migrations for customers, subscriptions, payments, invoices with:
Proper FKs (user_id → auth.users, stripe_customer_id → customers.stripe_customer_id)
UNIQUE constraints on all Stripe IDs
ENUM columns for subscriptions.status, invoices.status if desired
5.2 Standardize the Edge Function Pattern
Recommendation: Embrace the microservices approach already wired into your booking flow:
Use stripe-customer-api for customer creation/listing
Use stripe-payment-api for booking+charge
Use stripe-subscription-api for subscriptions
Use stripe-admin-api only for admin dashboards
Why: Smaller, single‑responsibility functions simplify local testing, CI, and rollback. They map directly to your frontend calls.
5.3 Remove Duplication & Align Helpers
Centralize in _shared/stripe-utils.ts:
Single getStripeCustomerId helper
Common error handling and API version setting
Delete overlapping code in stripe-api monolith or vice versa.
5.4 Harden Webhooks
Add idempotent upsert logic (.upsert(...)) based on UNIQUE Stripe IDs.
Standardize on one Stripe API version (e.g. 2024‑06‑20) in all functions.
5.5 Clarify Status Domains
Booking workflow: exclusively use booking_status enum.
Payment workflow: rename payment_status or use a new ENUM in payments table.
Update UI labels so users see “Payment Succeeded/Failed” vs. “Booking Scheduled/In Progress/Completed” independently.
5.6 Frontend Adjustments
In StripePaymentWeb.tsx, drop custom headers override so invoke() passes JWT.
Supply billing_details in confirmCardPayment.
Ensure EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY is set in all build environments.
6. Next Steps
Review & merge the missing migrations for Stripe tables.
Refactor your Edge Functions to the microservice pattern.
Align enums and status fields in local migrations with production.
Test end‑to‑end in Expo with test cards, covering success/failure & webhook retries.
Deploy and monitor logs, paying attention to duplicates or missing events.
